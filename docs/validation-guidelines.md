4. Match Levels and Region Strategy
4.1 Match Levels
Area	Match level	Reason
Global header, footer, breadcrumbs (structure)	Strict	Static chrome, must be pixel-stable
Forms and modals (empty state)	Strict	Labels, helper text and controls are static
Detail pages with record data	Layout	Structure matters; values vary
List/search result pages	Layout	Row count and content vary per environment
Charts / timelines with dynamic dates	Layout	Position of steps matters, text does not
Rich-text editor content area	Ignore region	User content
4.2 Dynamic Content (use dynamic regions where supported, otherwise ignore regions)

Treat as dynamic — never compare literally:

Record titles generated by automation (e.g. titles containing timestamps or numeric suffixes).
Record IDs (E0000xxx, RFP000xxxx, work order numbers).
Dates, date ranges, timestamps and "Last Updated" lines.
Currency amounts, rates, distances, totals.
Person names, email addresses, vendor names, org unit names.
Result counts ("N Results", "N items", "Page X of Y with N results", "0/2 Received", "/2 Scored").
Avatar initials.
Activity feed entries (validate the container and item layout; ignore text).
Notification dot on the Tasks icon (presence varies per user/session).
4.3 Floating Regions
"Contact Us" side tab — fixed to the right viewport edge; use a floating region with vertical tolerance. Still validate its shape and color strictly (Section 5.1).
Tooltips — floating region with ±8 px offset tolerance.
Dropdown menus and date pickers — floating relative to their trigger.
4.4 Accessibility Validation

Enable Eyes accessibility validation at WCAG 2.1 AA. Mark regions:

Body copy and helper text → regular text
Page titles and card titles → large text
Status badges and links → bold/regular text as rendered
Icons and icon-only buttons → graphical object
Disabled buttons → ignore contrast (disabled controls are exempt), but they must still be visually distinguishable from enabled ones
5. Design Guidelines (Validation Rules)

Each rule is a check to apply when reviewing a diff or a new baseline. "MUST" = defect if violated. "SHOULD" = flag for review.

5.1 Global Shell

Top header bar

MUST span the full viewport width at every breakpoint, with a white background and a subtle bottom shadow separating it from the page.
MUST show, left to right: navigation trigger (hamburger on narrow viewports, or full text navigation on wide desktops), a thin vertical divider, the Workday "W" logo mark (orange arc over navy W), and the product name in regular-weight dark gray.
Right cluster MUST show the Tasks control and the user menu (circular avatar + name + chevron). On narrow viewports the name and "Tasks" label MAY collapse to icons only.
The notification indicator, when present, MUST be a small solid red dot anchored to the top-right of the Tasks icon.
Header height MUST remain constant across pages (~60 px).

Breadcrumbs

MUST appear directly below the header, left-aligned with page content.
Ancestor items MUST be blue, underlined links; the current page MUST be dark, non-underlined, non-link text.
Separators MUST be small gray chevrons with equal spacing on both sides.
Long breadcrumbs SHOULD wrap to a second line rather than truncate or overflow.

Page title block

Page title MUST be the largest, boldest text on the page (dark near-black, ~32–40 px bold).
Long titles MUST wrap within the content column; they MUST NOT push action buttons off-screen or overlap them.
A status badge and the record ID MAY follow the title on the same baseline; the ID is gray regular text.
Create/edit pages MUST show a circular outlined back button to the left of the title, vertically centered with the first line of the title.
Page-level actions MUST align to the top-right of the title block on desktop and stack below the title on narrow viewports, preserving order.
Utility icon buttons (print, email, add document) MUST be equal-size outlined circles with consistent gaps.

Footer

MUST be centered: logo mark + divider + product name, then a line with the Privacy link and copyright text, then the Terms of Use link.
Links MUST be blue and underlined; copyright text MUST be gray and centered.
MUST have generous top spacing separating it from the last content card.

Floating "Contact Us" tab

MUST be a solid blue vertical tab anchored to the right edge, with rotated white text reading bottom-to-top and a small icon, rounded only on its left side.
MUST NOT cover primary actions, form inputs, status text or critical card content. Overlap with a button, a vendor/contact entry or helper text is a defect (see 7.2).
5.2 Color and Status Semantics
Role	Appearance
Primary action / active state	Solid brand blue (~
#0A5FD6) with white text
Links	Brand blue; underlined for navigational links, bold non-underlined allowed for in-card action links
Primary text	Near-black (~#333)
Secondary text (helper, meta, timestamps)	Mid-gray (~#666–#777)
Borders and dividers	Light gray (~
#D9D9D9–
#E5E5E5)
Required indicator	Red asterisk immediately after the label
Success / completed	Green (filled check circles, completed stepper dots and lines, add "+" icons in side cards)
Error / destructive state	Red

Status badges MUST be small, uppercase, bold, compact rounded labels placed next to the record title or in list rows, using this semantic mapping:

Semantic group	Example statuses	Badge style
Pending / awaiting action	Submitted	Pale yellow background, dark amber text
Positive / progressing / done	Approved, Sourcing, Awarded, Proposal Submitted	Pale green background, dark green text
Negative	Rejected	Pale red/pink background, dark red text
Neutral / inactive	Draft, Invited	Pale gray background, dark gray text
The same status MUST render with the same color everywhere (title block, list row, card).
A badge MUST NOT change color across environments; any color change is a defect.
Color MUST NOT be the only differentiator — the status word must always be present.
5.3 Typography
Level	Use	Style
H1	Page title	~32–40 px, bold
H2	Card title (Expenses, Activity, RFP Details, Vendors)	~20–22 px, bold
Section label	Form/card sections (GENERAL, CONTACTS, RESPONSE TIMELINE)	Uppercase, letter-spaced, semibold, ~16–18 px
Field label	Labels above inputs and data values	~15–16 px, medium/semibold
Body / value	Field values, list text	~15–16 px, regular
Helper / meta	Hints, "Action completed by", timestamps, counts	~13–14 px, regular, gray
Caption	"Approval Required", result counts	~12–14 px, italic, gray
Badge	Status	~11–12 px, uppercase, bold
One font family across the product (sans-serif, Roboto-like). A fallback font rendering is a defect.
Uppercase section labels MUST be visually distinct from card titles (letter spacing + uppercase, not just size).
Line height MUST keep multi-line labels and values readable; clipped descenders or overlapping lines are defects.
5.4 Layout, Spacing and Cards
Page content MUST have a consistent horizontal margin (~24 px on mobile, centered max-width container on desktop).
Cards MUST have: white background, 1 px light-gray border, large corner radius (~20–24 px), internal padding (~24 px), and a bold title at the top-left.
Vertical gap between stacked cards MUST be consistent (~24 px); horizontal gap between side-by-side cards MUST match it.
Side-by-side cards in a row (e.g. Activity + Approvals, Details + Vendors) MUST align their top edges.
Data inside cards uses a label-over-value grid: equal-width columns (up to 4 on desktop), consistent row gaps, label always directly above its value, left-aligned.
Grids MUST reflow from 4 → 2 → 1 columns as width decreases; values MUST NOT overlap adjacent columns.
Card action rows (e.g. item-level Approve/Reject) MUST sit at the bottom-left of the card content, below the data grid.
Header actions in a card (Edit link, "+" add icon, "View Approval Chain" link) MUST align to the right edge on the same line as the card title.
Dividers between list items MUST be full-width within the card and 1 px light gray.
5.5 Buttons
Variant	Appearance	Use
Primary	Solid blue fill, white bold text, fully rounded pill	The single main action in a group (Approve, Save, Add New, Send to Vendors)
Secondary	White fill, 1 px gray border, dark bold text, pill	Alternatives (Reject, Cancel, Adjust, Actions ▾, Bulk Upload)
Small	Same styles at reduced height/padding	Inline actions inside lists and approvals
Icon button	Outlined circle, centered icon	Print, email, kebab menu, back, filter, pagination arrows
Disabled primary	Washed-out light blue fill, white text, no hover	Action not yet available
Within any button group the primary button MUST be visually dominant and the group order MUST be consistent within a context (e.g. modal footers: primary first, then Cancel; inline item actions: Approve then Reject).
Buttons in the same group MUST share height and vertical alignment, with equal gaps.
Button text MUST stay on one line. Wrapped button labels are a defect.
Buttons with icons (e.g. "+ Add New", "Split Amount") MUST keep the icon left of the label, vertically centered.
Dropdown-trigger buttons MUST show a chevron to the right of the label.
Disabled state MUST be clearly distinguishable from enabled (lighter fill), and both MUST keep the same size.
5.6 Links
Navigational links (breadcrumbs, record titles in lists, work order references, footer, "Add Document", "View All", "+ Add Comment") MUST be blue and underlined.
In-card secondary action links ("View Comments and Rejection Reasons", "Show More", "Edit") are blue; they MAY be bold and non-underlined but MUST be consistent for the same link type across pages.
Links MUST NOT be styled identically to body text.
Centered "View All" links MUST be horizontally centered at the bottom of their card.
5.7 Form Controls

General

Every input MUST have a label above it, left-aligned with the input edge.
Required fields MUST show a red asterisk directly after the label text.
Helper text, when present, sits between the label and the control, in gray.
Text inputs, selects, date and time inputs MUST share the same height (~40 px), 1 px gray border, ~8 px corner radius and white fill.
Placeholder text MUST be lighter gray than entered values.
Paired fields (From/To Date, From/To Location, Category/Type, Amount/No Receipt) MUST sit side by side in two equal columns on desktop/tablet and keep their pairing order when stacked.

Specific controls

Select / dropdown — chevron at the right edge, vertically centered.
Searchable select — magnifying-glass icon on the left and a solid caret on the right; placeholder truncation with ellipsis is acceptable, overflow is not.
Date input — calendar icon on the left; a clear "×" on the right when a value exists.
Time input — clock icon on the left; the timezone label sits to the right of the time input, vertically centered with it.
Currency input — currency code prefix inside the field before the number.
Toggle — pill track with circular knob; off = gray track, knob left; on = brand color, knob right.
Checkbox — square, rounded corners; checked = blue fill with white check.
Rich-text editor — bordered container with menu bar, toolbar rows, and an editable area beneath; toolbar groups separated by thin dividers; toolbar MUST wrap cleanly inside its container on narrow widths.
Subsection headers inside forms (e.g. a "Cost Allocation Code" group) MUST have a full-width divider line beneath them.

Validation states

Error state MUST change the field border to red and show a red message below the field; label and layout positions MUST NOT shift other fields horizontally.
5.8 Modals / Dialogs
White surface with rounded corners (~12–16 px), centered over a dimmed backdrop.
Title in bold at the top (left-aligned for form modals, centered for selection modals — consistent per modal type); close "×" icon top-right, vertically aligned with the title.
Body content follows the form rules in 5.7. Selection modals place the search control inside a light-gray panel.
Footer separated by a full-width divider, containing primary (Save) then secondary (Cancel) buttons, left-aligned.
Save MUST be disabled until the minimum required input is present.
Long modals MUST scroll the body while keeping the title visible; content MUST NOT be cut off without a scroll affordance.
Empty-state text inside a modal (e.g. nothing added yet) MUST be centered in the content area.
5.9 Lists and Search Results

Toolbar

Search field with leading magnifier icon and, when filled, a trailing clear "×".
Result count immediately right of the search field, italic gray.
Sort control right-aligned with a "Sort" label to its left.
View toggle (list/grid), when present, is a segmented control; the active segment is solid blue with a white icon.
The toolbar sits in a light-gray rounded container spanning the list width.

Filter sidebar

Left column with a "Filters" header (icon + label) and a blue "Clear" link aligned right.
Each filter group is a collapsible row with a chevron; chevron points down when collapsed and up when expanded.
Group rows separated by thin dividers; checkbox options indent under their group.

Rows

Record title is a blue underlined link at the top-left of the row.
Status badge and primary metric (e.g. amount) sit on the line under the title, followed by secondary meta lines in smaller text.
Metadata columns use icon + label + value blocks; icons are small, gray, outline style and top-aligned with the label.
Metadata columns MUST align vertically across all rows.
Selection checkboxes appear only on actionable rows; rows without checkboxes MUST keep their content aligned with rows that have them (no horizontal jump of titles/metadata).
Indicator ribbons (e.g. an "awarded" marker on the left edge) MUST NOT misalign the row's title relative to other rows beyond the documented indent.
Rows separated by full-width light-gray dividers.

Bulk actions

"Select all on page" checkbox at the top-left of the list; bulk primary and secondary buttons at the top-right, small size.

Pagination

Centered below the list. Current page = solid blue circle with white number; previous/next = chevrons or outlined circular arrow buttons; disabled arrows are lighter gray.
Total item count or "Page X of Y" text centered beneath or between controls.
5.10 Tabs, Stepper and Checklists

Tabs

Horizontal tab row with a full-width light-gray baseline.
Active tab: blue text with a thick blue underline bar aligned to the tab width; inactive tabs: gray text, no bar.
Tab spacing MUST be equal; switching tabs MUST NOT shift the tab row.

Progress stepper (lifecycle timeline)

Horizontal line of evenly spaced nodes with labels centered beneath each node.
Completed steps: filled green dots joined by a solid line.
Current step: larger blue circle with a white icon and a soft halo.
Future steps: hollow gray circles joined by a dashed gray line.
Each label stack: step name (dark), primary detail (date/status), secondary caption (gray, smaller). An inline link in a step label MUST be blue and underlined.
Labels MUST NOT overlap neighbouring labels; on narrow viewports they wrap within their column.

Next-steps checklist

Each item: title + status sub-text on the left, state icon on the right.
Complete = filled green circle with white check. Incomplete = outlined circle with a green "+" (actionable).
Icons right-aligned in a single column.
The gating primary action below the list remains disabled until all required items are complete, with an explanatory caption beneath it.
5.11 Activity Feed, Approvals and People

Activity feed

Reverse-chronological list inside a card. Each item: event description (dark, regular), "Action completed by" line (gray, smaller), timestamp (gray, smaller), with consistent vertical rhythm.
Items separated by dividers inset to the card padding.
If the list scrolls, a subtle fade at the bottom is acceptable; content MUST NOT be hard-clipped mid-line.

Approvals

Approver name bold, with a gray "(You)" marker for the current user, an italic gray caption for the required state, and small Approve/Reject buttons beneath.
"View Approval Chain" link right-aligned on the card title line.
Comment section label uppercase gray, with "+ Add Comment" link right-aligned on the same line.

People / vendor entries

Name bold, then contact line, then email in smaller gray text; a status badge MAY sit to the right of the name.
Per-entry overflow menus (kebab) are outlined circular icon buttons right-aligned and vertically centered on the entry.
Avatars are circles: initials avatars either outlined gray (collaborator list) or solid blue with white initials (contact cards). Avatar groups MUST be left-aligned with the content below them, with a consistent gap to the "add person" button.

Tooltips

Dark (near-black) background, white text, small radius, positioned adjacent to the trigger without covering it.
5.12 Empty States
Centered, gray or dark regular text describing the empty condition, inside the card/modal content area.
When an action is available, a secondary button sits centered beneath the text.
The card retains its normal title and padding; it MUST NOT collapse to zero height.
5.13 Data Formatting Patterns (validate format, not value)
Data	Expected pattern
Date	Mon D, YYYY (abbreviated month, no leading zero)
Date-time	Mon D, YYYY, h:mm AM/PM plus timezone abbreviation where shown
Date range	Same month: Mon D – D, YYYY with an en dash and spaces
Currency	Currency code + space + amount with exactly 2 decimals; negatives prefixed with a minus before the code
Distance / quantity	Two decimal places
IDs	Prefix letters + zero-padded number, gray when beside a title
Counts	Plural-aware ("1 Result" vs "2 Results")

A visible format deviation (e.g. raw ISO dates, missing decimals, NaN, undefined, null, empty placeholder where a value is expected) is a defect, even inside dynamic regions.

5.14 Iconography
Single outline icon family, consistent stroke weight, gray for metadata and dark for actions.
Icons vertically centered with their text label.
Icon-only controls MUST have a visible boundary (outlined circle) or a tooltip.
Missing icons (empty boxes, broken glyphs, alt text) are defects.
5.15 Responsive Behavior
No horizontal scroll of the page body at any viewport. Every element (including date/time rows with timezone labels, header bar, cards) MUST fit within the viewport width.
The header MUST stretch edge to edge; a header narrower than the page is a defect.
Form cards MUST fill the available content width on mobile; labels and helper text MUST NOT be squeezed into a narrow column while empty space remains beside them.
Multi-column grids collapse to fewer columns; side-by-side cards stack vertically in DOM order.
Desktop top navigation collapses into the hamburger menu below desktop widths.
Page title action buttons move below the title, keeping their order and size.
Buttons MUST keep single-line labels; if space is insufficient, the button grows in width or stacks, never wraps text.
Fixed/floating elements MUST NOT obscure content or controls at any viewport.
5.16 Accessibility (visual aspects)
Text contrast ≥ 4.5:1 (≥ 3:1 for large text) against its background, including gray helper text and badge text on tinted backgrounds.
Focus states MUST be visible on all interactive elements (outline or ring) when tabbed to.
Interactive targets ≥ 24×24 px; icon buttons SHOULD be ≥ 40×40 px.
Required state MUST be conveyed by the asterisk (and programmatically), not color alone.
6. Severity Classification
Severity	Examples
Critical	Primary action hidden, covered or clipped; page content overflows viewport; modal cannot be closed or saved; wrong status badge color/semantic; header/footer missing
Major	Floating element overlaps content; button label wraps; grid columns overlap; misaligned card rows; wrong font family; broken icons; format errors (NaN, raw dates); missing required asterisk; contrast failure
Minor	Spacing deviation > 4 px; inconsistent link underline for same link type; inconsistent icon size; tooltip offset; uneven gaps in button groups
Ignore	Data value changes inside dynamic regions; sub-pixel anti-aliasing; scrollbar rendering differences between browsers; the presence/absence of the notification dot
7. Known Anti-Patterns to Watch For

These issue types have been observed in this product's UI and MUST be checked explicitly on every run:

7.1 Narrow-viewport layout breaks
Form card not stretching to full width, leaving labels and helper text wrapped into a thin column.
Date + time + timezone rows extending outside the card or viewport.
Header bar rendering narrower than the page content.
Rich-text toolbar wrapping into fragmented rows inside an undersized editor.
7.2 Floating element collisions
The "Contact Us" tab covering card content, vendor entries, primary buttons or explanatory captions near the right edge.
7.3 Inconsistent alignment between states of the same page
The same component (e.g. collaborator avatar group, action buttons) positioned differently between lifecycle states of the same record page. Compare states side by side; alignment must be identical unless the design intentionally changes.
7.4 Wrapped button labels
Buttons inside narrow cards (e.g. an "Add Documents" button in an empty state) wrapping onto two lines.
7.5 Row misalignment in lists
Titles and metadata shifting horizontally between rows with and without checkboxes or indicator ribbons.
8. Resolution Rules for the Assistant

When using eyes_review_* / eyes_resolve_*:

Accept a diff only if every change is explained by dynamic data (Section 4.2) or an intentional, documented design change, and no rule in Section 5 is newly violated.
Reject / mark as bug any diff that introduces a Critical or Major item from Section 6, or that matches an anti-pattern in Section 7.
Do not auto-accept a new baseline that already contains a Critical or Major violation; flag it for human review with the rule number violated.
When the same diff appears across many checkpoints (e.g. a header change), resolve it once and propagate, but list every affected page in the summary.
If a diff is caused by test flakiness (late-loading content, animation mid-frame), recommend the stabilizing fix (wait condition, region, animation disable) rather than accepting.
Always report findings in this shape:
Page / State:   <checkpoint name>
Viewport:       <browser @ width>
Rule violated:  <section number + rule summary>
Severity:       Critical | Major | Minor
Evidence:       <region/coordinates or element description>
Recommendation: Fix in UI | Update baseline | Add region | Stabilize test
